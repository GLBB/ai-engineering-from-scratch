## 先记住两句话

**Agent Loop：**模型根据当前历史决定下一步，宿主执行工具，把结果送回模型，直到正常结束或触及运行边界。

**ReWOO：**先生成带证据引用的计划，执行器沿依赖取回证据，最后由 Solver 汇总；减少规划与观察反复交织的成本。

两章的连接点是：第一章把“下一步由谁决定、工具如何执行”讲清楚，第二章把“何时规划、哪些信息需要反复交给模型”拆开。

## 模式对照速查

| 维度 | ReAct 式循环 | ReWOO | 带重规划的 Plan-and-Execute |
| --- | --- | --- | --- |
| 下一步何时决定 | 每轮观察之后 | 执行前写出计划和引用 | 先规划，执行中按策略修订剩余计划 |
| 新观察是否影响计划 | 可以影响下一步 | 静态规划阶段不读取本轮工具观察 | 可以通过 Replanner 影响 |
| 工具结果放在哪里 | 对话历史 | 按节点 ID 保存的 evidence | 执行状态、证据和剩余计划 |
| 并行机会 | 一轮中的独立调用 | DAG 中依赖已满足的独立节点 | 取决于当前计划与执行器 |
| 主要优势 | 适应未知环境和临时变化 | 依赖显式、可定位失败、减少重复上下文 | 保留计划结构并适应变化 |
| 主要代价 | 历史反复携带、路径可能漂移 | 初始计划错误会影响后续节点 | 重规划需要额外成本和终止规则 |

这些模式可以组合：外层维护计划，内层执行某个步骤时使用 Agent Loop。Planner、Worker、Solver 是职责，不必是三个模型，也不必是三个进程。

## 本次特别补充的内容

1. **三个不同的完成标准：**服务端接受请求、循环正常退出、用户任务完成，需要分别判断。
2. **三种不同的成本：**模型调用次数、token/费用、端到端耗时，不能互相替代。
3. **两个不同的 ID：**第一章协议调用 ID 与界面轨迹 ID；第二章还要区分计划节点 ID。
4. **代码边界：**第一章的执行上限只在实验中演示；第二章尚无并发执行、结构化失败和自动重规划。
5. **可验证的下一步：**每个 TODO 都配验收条件，避免只勾选“看懂了”。
