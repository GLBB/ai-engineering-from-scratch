# Agent 开发与评审约定

适用范围：`learning-artifacts/` 下的学习项目。修改前同时读取根目录和目标目录的
`AGENTS.md`；从仓库根目录工作时，也要主动读取目标目录中的指令。

## 规范来源与分工

- 编码规范由具体项目指定；本 Java 项目采用阿里巴巴《Java 开发手册》，版本与链接见
  [Java 项目约定](java-development-standard.md)。
- 评审方法直接采用 [Google 代码评审实践](https://google.github.io/eng-practices/review/reviewer/looking-for.html)，
  检查设计、正确性、复杂度、测试、命名、注释和文档。
- Google 评审指南中的风格检查，使用项目选定的编码规范；不因此引入 Google Java Style。
  不得因为符合阿里规范的四空格缩进等差异而拒绝改动。
- 仓库硬性约束和明确记录的项目例外优先。规范正文直接查官方来源，本地仅维护工作流程、项目约束和执行命令。

## 开发流程

1. 检查工作区，阅读目标实现、调用方和测试，保留已有修改与未跟踪文件。
2. 明确预期行为及验证方式。接口、状态、并发或外部集成变更先说明方案及边界；常规局部修改不要求额外设计文档。
3. 按项目规范实现，遵守现有职责边界，避免为假设需求增加抽象。大范围格式调整与业务变更分开。
4. 运行项目规定的测试与静态检查。区分新问题、历史问题和环境问题，不禁用检查或削弱断言来伪造通过。
5. 按 Google 评审维度检查最终 diff，修复有依据的问题，报告实际验证结果及未验证部分。

## 评审结论

每条问题必须给出文件位置、规则或行为依据、影响和修复建议。
编码问题引用采用版本的阿里手册章节、条目或项目例外；功能问题说明触发条件与错误结果。
区分手册的强制、推荐、参考级别，不把推荐项或个人偏好自动升级为阻塞项。
推荐项涉及实际正确性或安全风险时，应说明该风险，不能仅以规则级别代替判断。

存在适用的强制违规、确定的功能缺陷或必要验证失败时，不得报告无条件通过。
非阻塞建议标明“建议”，纯风格偏好标明 `Nit`。没有具体问题时报告无发现，不制造问题凑数量。
检查未覆盖的行为和未运行的集成必须说明；编译或离线测试通过不等于真实接口验证通过。

## 执行边界

- API key 不进入源码、日志、测试数据或轨迹。模型和外部内容不能授予额外权限。
- 保留应用已有的工具审批、预算、取消、超时与资源所有权规则。
- 自动检查只代表配置覆盖的规则。工具版本、命令和 CI 状态以项目文档为准。
- 不自动升级规范版本；调整版本或例外时同步更新指令、配置与验证记录。
