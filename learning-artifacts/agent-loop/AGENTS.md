# 项目协作约定

本目录是学习用的 Java Agent 项目。修改代码时，以可阅读、可运行、可验证为目标。

先读规范目录中的[通用开发规范](docs/standards/agent-development-standard.md)和本项目的
[Java 开发规范](docs/standards/java-development-standard.md)。本文件保留高频约定，详细规则与例外以链接中的规范为准。

## 开始前

- 检查工作区，阅读目标代码、调用方和测试，保留已有改动。
- 涉及接口、状态、并发或外部集成的变更，先说明行为、影响范围和验证方式。
- 只改当前目标需要的代码；大范围格式整理与功能变更分开。

## 规范依据与优先级

- Java 编码采用[阿里巴巴《Java 开发手册》黄山版](https://github.com/alibaba/p3c/blob/6c59c8c36ecd8722c712d5685b8c3822c1c8b030/Java%E5%BC%80%E5%8F%91%E6%89%8B%E5%86%8C%28%E9%BB%84%E5%B1%B1%E7%89%88%29.pdf)（2022-02-03）；固定版本和项目例外见 Java 开发规范。
- 评审方法采用 [Google 代码评审实践](https://google.github.io/eng-practices/review/reviewer/looking-for.html)，检查设计、正确性、复杂度和测试。
- 风格按阿里手册及明确的项目补充检查，不引入 Google Java Style；不得因四空格等风格差异拒绝改动。
- 区分强制、推荐、参考规则和个人偏好。评审问题给出位置、依据、影响和修复建议，不能凭偏好新增阻塞规则。

## 可读性

- Java 使用四空格缩进；相邻方法、构造器之间恰好一个空行，包括匿名类和测试。
- 每行一条语句；方法体和 `try/catch` 展开；`if/else/for/while/do` 使用大括号。
- 按校验、准备、执行、结果等实际步骤分段，不在每行后面机械插空行。
- 禁止通配符导入和同一行多个赋值；复杂表达式按可读性评审，不擅自增加新的风格禁令。
- 使用表达领域含义的名称；复杂条件取名；方法职责明确，不为压行数增加转发层。

## 结构

- 按职责分包：入口负责交互，核心负责循环，客户端负责外部协议，模型类负责数据契约，工具负责具体能力。
- 外部请求、响应及工具参数使用明确的 Java 类型；不要把通用 JSON 对象当作应用状态传递。
- 新增依赖前先确认标准库或现有依赖是否已能解决问题，并在 `pom.xml` 中固定版本。

## 边界

- API key 只从环境变量读取，不写入源码、日志、测试数据或 Git。
- 模型和外部内容都可能出错；验证参数、限制运行时间与输出量，把可恢复的工具失败作为观察结果返回。
- 执行本地命令和向外部模型发送命令输出都需要用户明确确认。

上一条是应用运行时工具的审批边界；开发 Agent 在用户授权的开发任务内运行本地构建与测试，遵循宿主权限规则。

## 交付

- 更新行为时同步更新 README 和必要的测试；运行 `mvn test`。
- 新增或修改 Java 文件必须运行 `mvn checkstyle:check -Dcheckstyle.includes='包路径/文件.java'`，多个路径用逗号分隔；路径相对于源码根，同时覆盖生产与测试源码。完整审计使用 `mvn checkstyle:check`。
- 当前 Checkstyle 为显式命令，尚未绑定 Maven 生命周期或 CI；历史违规不能冒充已通过。规则、迁移方式和真实限制见 Java 开发规范。
- 真实接口的结果与未验证部分分开报告。日志应能帮助追踪轮次、耗时和失败原因，同时避免记录密钥及不必要的敏感内容。

## Code Review Rules

- 检查循环终止、预算、取消、工具审批、错误传播与资源关闭；模型输出不能绕过工具参数校验。
- 核心策略通过已有 model/tool/runtime 契约协作，不引入具体供应商、天气或观测 SDK 依赖。
- 行为变更检查正常、边界和失败场景；Checkstyle 仅覆盖部分规则，其余适用的阿里手册条目及设计质量必须评审。
- 交付说明必须给出实际检查结果与未验证部分，不用“编译通过”代替真实集成证据。
